# Real-software tasks

Status: proposed (study 3), to be accepted after the pilot

Study 3 asks where code lives in real open-source programs instead of asking for a crackme input. The sources are official release archives listed in `sources.json` with their SHA-256 and licence, downloaded and verified by `scripts/setup.mjs --manifest sources.json` into the ignored `tools/sources/`; no third-party executable is ever downloaded. `challenges/real.mjs` compiles every translation unit with llvm-mingw (x64, `-O2`, `-static`, no LTO, `-ffunction-sections -fdata-sections`, `-g`, prefix maps, `NDEBUG`) in a fixed order and links with `--icf=none`, `--gc-sections`, a linker map, no timestamp and no build id. lld keeps the per-function sections in input order, not sorted by name, so the layout tells nothing about the source names. The target is the same image after `llvm-objcopy --strip-all`: the build checks that every non-debug section is identical and that a second build gives the same target hash, so addresses in the target are the addresses of the full build. lld still writes one CodeView debug record, all zeros, without a path or an identifier; the check accepts it only in that form.

Ground truth comes from the full build: function and data ranges and their owning object from the linker map, cross-checked with the symbol table and `.pdata`, inlining from `llvm-symbolizer --inlines`, and direct calls and RIP-relative references from `llvm-objdump`. A validator keeps only unambiguous targets (not inlined anywhere, no identical twin or duplicate name, no clone suffix, not a thunk, not toolchain code, not the program entry) and checks that the target image has no exports, symbols, debug data or personal paths.

Each run asks one question, and the answer is a virtual address, which depends on the build, so remembering the source does not give it. It is graded by range: correct when it falls inside `[start, end)` of the target, with the exact start as a secondary outcome; a relative address counts but is flagged. Every family is defined by a property the validator checks in the binary: `string` (the only code reference to a message, used as a control), `behaviour` (no direct string reference), `caller` (the only direct caller of a string-anchored function whose address is never taken) and `data` (a named table referenced from code). Targets are drawn with a private seed from the validator's eligible list; the author only writes the descriptions and records why any candidate is dropped. The task file's hash is published before a study, and the tasks, the ground truth and the seed after.

Known limitations: the mingw ABI and runtime, not MSVC; well-known projects are familiar to the model and their version strings can name the program, so the scope is locating known open-source code in a stripped static binary, not recognising unknown software.
